## Booking and lead data flow

1. Visitor interacts with Sera v9 on the static site.
2. Browser posts same-origin JSON to `/api/leads.php`.
3. PHP loads a private configuration containing the Apps Script `/exec` URL and shared API key.
4. PHP forwards HTTPS-only JSON to Apps Script.
5. Apps Script validates the shared key, request ID and payload.
6. Enquiries are persisted in the private Leads sheet.
7. Bookings recheck Calendar free/busy under a script lock before insertion.
8. A deterministic Calendar event ID is derived from the request UUID, making retries idempotent.
9. Calendar/Meet status is recoverable by the same request UUID.
10. Notification work is processed separately; a booking record is not duplicated if notification or transport state is uncertain.

## Security / threat baseline

### Existing controls

- API and AI credentials remain server-side.
- Lead POSTs require the production Origin header at the Hostinger gateway.
- Hostinger lead gateway accepts only known actions and UUID references.
- Request bodies, contact fields, services and brief sizes are bounded.
- Honeypot field rejects basic automated submissions.
- Temporary-file rate limiting hashes the visitor IP with the private key.
- PHP cURL forwarding is HTTPS-only and targets a configured Google Apps Script URL.
- Calendar writes are rechecked against live free/busy state under a lock.
- Unknown network/write outcomes become `pending`; clients reuse the same reference instead of generating a second booking.
- Deterministic event IDs and payload fingerprints protect retry/idempotency behavior.
- Spreadsheet-formula injection is escaped before persistence.
- Email HTML escapes user content.
- Sera strips recognisable emails, phone numbers and URLs before provider submission.
- Sera AI requires explicit consent and has a deterministic non-AI fallback.
- Booking notification waits for a ready Meet URL before sending the meeting-link notification.

### Residual V0.1 risks

- The active private Hostinger config and active Apps Script deployment/version still require owner-side verification before release.
- The PHP rate limiter uses temporary host storage, so durability/cluster behavior depends on Hostinger runtime.
- No production E2E test currently proves browser → PHP → active Apps Script → Sheet → Calendar → Meet on the live account.
- There is no verified monitoring/alerting path for repeated gateway or Calendar failures.
- No analytics instrumentation is verified.
- The legacy unused `LeadForm` path has weaker pending-state UI semantics than Sera v9 and must not become an active booking surface without remediation/tests.
- The orphaned hero-lock contract should be replaced by a reproducible generated lock or removed through an explicit design-system decision.
